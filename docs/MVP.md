# MVP.md — Weather App

## 1. Project Goal

Build a small, functional, visually appealing weather application within **120 minutes**. Code may be generated by an AI coding agent, with the human supervising scope, architecture, implementation, and verification.

**Priority order:** working application → clear and attractive UI → understandable code and proportionate SOLID practices. Avoid overengineering.

This document defines the product scope and constraints. The implementation task map should be created separately after the agent inspects the repository.

## 2. Technology Stack

- React
- Vite
- TypeScript
- Tailwind CSS
- Axios for HTTP requests
- OpenWeather API for geocoding and current weather
- SOLID principles applied pragmatically

- Geocoding API: https://openweathermap.org/api/geocoding-api
- Current Weather API: https://openweathermap.org/api/current

## 3. MVP Features

### Required

1. Search for a city by name.
2. Resolve the city to geographic coordinates using OpenWeather Geocoding API.
3. Fetch current weather using OpenWeather Current Weather API.
4. Display:
   - City and country when available
   - Current temperature in Celsius
   - Weather description and weather icon
   - Feels-like temperature
   - Humidity
   - Wind speed
5. Provide clear states for:
   - Initial/empty view
   - Loading
   - Successful result
   - City not found
   - API or network failure
6. Provide a clean, attractive, responsive interface for mobile and desktop.
7. Pass TypeScript checks and produce a successful production build.
8. **Arabic, right-to-left user interface (mandatory).** See section 4a.

### Out of Scope

- Authentication or user accounts
- Backend or database
- Multi-day or hourly forecasts
- Saved/favourite cities
- Maps, charts, air quality, or alerts
- Complex global state management
- Routing for multiple pages
- Large UI component libraries
- Extra features that threaten the two-hour timebox

## 4. OpenWeather API Integration

Use the documented OpenWeather endpoints.

### City geocoding

`https://api.openweathermap.org/geo/1.0/direct?q={city_name}&limit=5&appid={API_KEY}`

- Treat an empty result as “City not found”.
- If multiple matches are returned, choose the best straightforward behavior. A small selection list is optional only if it fits the timebox.
- Do not use deprecated city-name lookup behavior in the Current Weather endpoint.

### Current weather

`https://api.openweathermap.org/data/2.5/weather?lat={latitude}&lon={longitude}&units=metric&lang=ar&appid={API_KEY}`

- Use coordinates returned by geocoding.
- Use `units=metric` for Celsius and metric wind speed (m/s).
- Use `lang=ar` so `weather[].description` is returned in Arabic. If the description is missing, use a generic Arabic fallback; do not show English text.
- City display name: prefer the geocoding result's `local_names.ar` when present, otherwise fall back to `name`. Arabic city input (e.g. `القاهرة`) must be accepted and URL-encoded.
- Map provider responses to an application-level weather model so UI components do not depend on the full provider response shape.
- Use OpenWeather's weather icon URL if useful; do not install an icon package just to display weather-condition icons.

## 4a. Arabic Language and RTL (Mandatory)

The entire user interface is in Arabic. This is a required feature, not an optional enhancement.

- `index.html`: `<html lang="ar" dir="rtl">` and an Arabic `<title>`.
- All visible text is in Arabic: page heading, search label and placeholder, button, weather descriptions, detail labels (feels like, humidity, wind), loading, empty-state, city-not-found, and error messages, plus image `alt` and `aria-label` text.
- Keep UI strings in one small module (e.g. `src/i18n/ar.ts`) rather than scattered literals. No i18n library.
- Service errors are typed codes; the UI maps them to Arabic messages. Never display raw Axios/provider error text.
- Use Tailwind's logical, RTL-aware utilities (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`, `text-start`, `text-end`) instead of `ml-*`/`mr-*`/`left-*`/`right-*`. Use `rtl:`/`ltr:` variants only where a directional icon must flip.
- Units: temperature in °C (`°م` acceptable), wind in `م/ث` (m/s), humidity in `%`. Western digits (0–9) are acceptable; Arabic-Indic digits are optional via `Intl.NumberFormat('ar')` if consistent throughout.
- Use an Arabic-capable font: a system stack is acceptable; a single Google Font (e.g. Cairo or Tajawal) via `<link>` is allowed, no font package.
- The layout must render correctly in RTL on mobile (≈375px) and desktop, with no mirrored-incorrectly or overflowing elements.
- Code identifiers, filenames, comments, and Git commit messages remain in English.

## 5. API Key Configuration

- Read the existing project configuration before making changes.
- Use a local `.env` file with a Vite variable such as `VITE_OPENWEATHER_API_KEY`.
- Ensure `.env` is ignored by Git.
- Add `.env.example` with a placeholder only; never commit the real key.
- For this local, non-public MVP, a Vite environment variable is acceptable for convenience. **A `VITE_` variable is bundled into client-side code and is not secret.** Revisit key protection before any public deployment.

## 6. Axios and Dependencies

### Required

- `axios` for HTTP requests and consistent request/error handling.
- The selected React, Vite, TypeScript, and Tailwind CSS stack.

### Optional — add only with a clear reason

- `lucide-react`: only if general UI icons materially improve the interface.
- `zod`: only if runtime validation of external responses is needed and fits the timebox.

Do not add Redux, Zustand, React Router, a date library, a UI framework, or other packages for this single-page MVP unless repository inspection reveals a concrete need.

**Dependency rule:** Every new dependency must solve a real requirement. Prefer the smallest useful solution.

## 7. Suggested Architecture

Keep the architecture small and understandable. Inspect the existing repository first and adapt this suggestion to its actual state; do not recreate or restructure a working project unnecessarily.

```text
src/
  api/
    openWeatherClient.ts
  services/
    weatherService.ts
  components/
    SearchBar.tsx
    WeatherCard.tsx
    WeatherDetails.tsx
  types/
    weather.ts
  i18n/
    ar.ts
  App.tsx
  main.tsx
  index.css
```

Suggested responsibilities:

- `api/openWeatherClient.ts`: Axios configuration and low-level HTTP requests.
- `services/weatherService.ts`: geocoding, current-weather retrieval, response mapping, and service-level error handling.
- `types/weather.ts`: domain types and useful API response types.
- `i18n/ar.ts`: all Arabic UI strings and the error-code → Arabic message map.
- `components/*`: presentation and user input; no raw HTTP calls inside visual components.
- `App.tsx`: coordinates search and page-level loading, success, and error states.

This structure is guidance, not a requirement to create every file. Avoid factories, repositories, extra abstraction layers, or dependency-injection infrastructure unless they solve a demonstrated problem.

## 8. SOLID Guidelines

Apply the principles proportionately to the size of the application.

- **S — Single Responsibility:** Separate HTTP communication, weather-service logic, and UI presentation.
- **O — Open/Closed:** Keep the weather-service boundary sufficiently clear that a provider implementation could be replaced without rewriting the UI.
- **L — Liskov Substitution:** Any alternative service implementation should preserve the same contract and expected behavior. Do not add artificial abstractions just to demonstrate this principle.
- **I — Interface Segregation:** Prefer small, focused TypeScript contracts and types.
- **D — Dependency Inversion:** UI orchestration should depend on the weather-service contract rather than directly on OpenWeather endpoint details.

The goal is low coupling and clear responsibilities—not maximum abstraction or maximum file count.

## 9. Timebox

The total working time is **120 minutes**. The AI agent should propose a small, practical task map after inspecting the repository. Use the following allocation as a planning guide, not as a rigid requirement:

## 10. Git and Commit Rules

- Make a commit whenever a **small, logically complete unit of work** has been implemented and verified.
- Do not commit unfinished, broken, or unrelated changes.
- Keep commits atomic: one commit should describe one coherent change.
- **Commit subject/title: maximum 50 characters.**
- **Commit body: maximum 200 characters**, explaining what the completed unit does or changes.
- Use a clear conventional-commit-style subject when practical, for example: `feat: add city search`.
- Keep the body concise, factual, and focused on the completed work.
- Do not combine multiple unrelated tasks in one commit merely to reduce the commit count.
- Do not create a commit for every tiny edit; commit completed, meaningful units.
- Never commit `.env` or a real API key.
- Do not push, open a pull request, merge, or change branches unless explicitly instructed by the human supervisor.
- Before committing, inspect the diff and run the relevant available check.

## 11. AI-Agent Working Rules

- First inspect the repository, existing files, package scripts, dependencies, Git status, and current branch.
- Do not assume the repository is empty or overwrite existing work.
- Initially, produce a concise task map only. **Do not start implementation until the human approves the map.**
- Avoid excessive task decomposition. A task should represent a meaningful, testable unit of work—not an individual file or tiny coding action.
- Prefer the fewest tasks that still provide clear boundaries and checkpoints; approximately 5–8 tasks is a guide, not a mandatory count.
- Each task should state its goal, scope, dependencies, acceptance criteria, and expected verification.
- Keep the project attractive and functional. Do not sacrifice the working product to pursue architectural perfection.
- Follow the commit rules above after implementation is authorized.
- Report blockers and trade-offs early instead of silently increasing scope.

## 13. Definition of Done

The MVP is done when a user can search for a city and view real OpenWeather current conditions in a clean, responsive, fully Arabic RTL interface, essential failure states are handled, responsibilities are reasonably separated, and the project builds successfully.

Anything not completed within the two-hour timebox should be listed as deferred work. Do not silently expand the scope.
